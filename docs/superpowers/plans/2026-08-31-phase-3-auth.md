**They are all forms, and `<x-field>` already does the work** — label, control, hint, and a

`.guest__panel` at 26rem, `.guest__brand`) and `layouts/app`. **There is no new page chrome
to design.** That is the main reason this phase should move faster than Phase 2, where every
page brought its own hero, panel and grid.

## The decision that shapes the phase — settle it in Task 1

**Which register do auth pages belong to?**

They are neither dashboard nor marketing.

> **Pre-flight correction.** This plan first claimed the guest shell sits outside
> `PublicRegisterTest`'s fence. It does not. The fence allows `2-layout/_shell-public.css`,
> and **that one file defines both shells** — `.public`, `.public__main`, `.public__footer`
> *and* `.guest`, `.guest__panel`, `.guest__brand`. So the guest shell is already inside the
> public register's fence, by accident of file organisation rather than by decision.
>
> That is a hole in the guard: someone could put a gradient on `.guest__panel` today and no
> test would object, even though nobody ever decided auth pages belong to the public
> register. **Whichever way the register question is answered, split that file** —
> `_shell-public.css` and `_shell-guest.css` — and put only the one that should carry
> gradients on the allowed list. A fence that permits something by accident is not a fence.

Today auth pages *render* with the dashboard's flat, hairline treatment, because nothing in
`_shell-public.css` actually uses a gradient token on `.guest`. That is convention, not
enforcement.

**Recommendation: keep them there.** Signing in is entering the app, not being sold it, and
the guest panel is 26rem of mostly form controls — the surface a gradient would sit on is
almost entirely input fields. The one concession worth making is the brand mark at the top
of the panel, which already renders `<x-brand>`.

Either answer requires the file split above; they differ only in which half lands on the
allowed list. **Do not start Task 2 until this is answered** — it determines every panel and
button treatment in the phase.

## Global constraints

1. **Never run git commands.** The owner runs every git operation manually, read-only ones
   included. To see what changed, use `find resources -newer <file>`.
2. **Screenshot every page before calling it converted.** This is the lesson of Phase 2, not
   a nicety: invisible gradients, a double-escaped apostrophe, a 300px layout hole and an
   unreadable panel all passed every computed-style assertion and were obvious in a
   screenshot. Chromium under snap confinement cannot write to `/tmp` — write to `$HOME`.
3. **A modifier always accompanies its base.** `ModifierClassGuardTest` enforces it.
4. **No inline CSS**, attribute or `<style>` block. `InlineStyleGuardTest` enforces it.
5. **Remove Tailwind from an element in the same edit that adds a design-system class.**
   Tailwind still loads after the system, so at equal specificity the utility wins and the
   new class silently does nothing.
6. **Update `ConvertedViewsTest::NOT_YET_CONVERTED` as each view lands.** The test fails if a
   converted view stays on the list, so this cannot be forgotten — but do it per task, not in
   a lump at the end, or the guard covers nothing for the whole phase.

## Task 2: `auth/login` and `auth/forgot-password`

**Files:** `auth/login` (159), `auth/forgot-password` (126)

`login` carries three things `<x-field>` does not cover:

- a **remember-me checkbox** — `<x-field>` renders a text input or a slot; a checkbox with
  an inline label needs its own treatment. If more than one view wants it, add
  `.field__check` to `_form.css` rather than styling it in the view.
- a **"forgot password?" link** beside the submit
- a **register link** in the panel header

`forgot-password` is one field plus a status message, and already uses
`<x-auth-session-status>`, which Phase 1 Task 12 converted to `<x-alert variant="success">`.

**Watch for:** `AuthenticationTest` covers login behaviour, but nothing asserts the
remember-me checkbox is present and named `remember`. Confirm by hand that it still posts.

## Task 3: `auth/register`

**Files:** `auth/register` (192)

The largest, and the page a new player meets first — worth the care `home` got.

Five fields: `first_name`, `last_name`, `email`, `password`, `password_confirmation`. All
plain `<x-field>` work. `RegistrationTest` covers the behaviour.

**Watch for:** the guest panel is **26rem**. Five stacked fields in a 26rem column is a long
scroll. Consider pairing `first_name` / `last_name` on one row with `.l-grid`, as `contact`
does for name/email — but check it at 375px, where the pair must collapse.

## Task 4: `profile/…/update-profile-information-form`

**Files:** the partial (94)

The only view in this phase with a **file upload and an image preview**, and the only one
`<x-field>` genuinely does not cover: `<input type="file">` needs its own control styling,
and the avatar preview beside it is a layout, not a field.

- Add `.field__file` to `_form.css`. Style `::file-selector-button` — the default is an
  OS-native button that ignores every token in the system.
- The preview is `<x-avatar size="lg">`, which exists.
- The form is `enctype="multipart/form-data"`. **Do not lose that attribute.**
  `ProfilePictureTest` will catch it, but only on upload, not on render.

**Watch for:** this form also carries `nickname` and, for admins, `is_admin`. The nickname
feeds the standings naming rule from Phase 1 Task 10 (nickname, else full name) and the top
bar's `display_name`. Do not drop the field.

## Task 5: `profile/edit`, `update-password-form`, `delete-user-form`

**Files:** three views, 79 utilities between them

`profile/edit` is a wrapper: a page header plus three partials. It already uses
`<x-page-header>` from Phase 1 Task 8's standard.

**`delete-user-form` holds the modal, and the modal needs hand verification.** Phase 1 Task
12 fixed its focus trap and scroll lock — `x-init` + `$watch` never fired on initial mount,
so a modal rendered with `:show="true"` (the wrong-password path) trapped nothing and locked
nothing. That fix has **never been exercised in a real browser**: headless Chromium cannot
drive Alpine's `x-show`, which was established in Phase 1. `ProfileTest` covers the reopen
server-side; the focus and scroll behaviour is only checkable by hand.

**Verify by hand:** submit the delete form with a wrong password, then confirm the modal
reopens, focus moves into it, Escape closes it, and the page behind does not scroll.

## The legacy components: a note for Phase 5, not a task here

Converting these ten views leaves the Breeze wrappers alive:

```
input-label 23   text-input 23   input-error 23   primary-button 23
secondary-button 1   danger-button 1   auth-session-status 2   modal 1
```

Those 23-call-site counts are **admin CRUD forms**, not these views. Phase 3 can move its own
ten to `<x-field>` and `<x-btn>`, but **cannot delete a single component** — Phase 5 owns
that. Expect the counts to fall from 23 to roughly 20 and no further, and do not treat that
as a failure.
